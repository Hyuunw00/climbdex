# 실험 2. 시도 분석 (동작 코칭)

떨어진 시도 영상을 보고 "다음엔 뭘 다르게 해야 하는가"를 말해 주는 기능. 앱 UI 전에 맥 스크립트로 되는지 확인한다. 실패 판정 기준을 먼저 적고, 통과한 것만 앱으로 옮긴다.

## 목표와 경계 (2026-09-30 결정)
- 목표: 완등 실패 영상을 넣으면 다음 시도에서 붙게 돕는다. 완등 영상도 같이 넣는다(비교 기준, 라벨)
- **안 만드는 것**: 사지별 힘 %(영상에 힘 정보가 없고 네 점 지지의 힘 분배는 물리적으로 하나로 정해지지 않음), 완등 확률(그 문제를 푼 데이터가 있어야 함), 다음 홀드 추천(확률 대신 "닿는 후보"까지만). 숫자를 지어내지 않는다
- 첫 버전의 상한은 **기술 코칭**이다. 벽을 못 보는 코치가 하는 말 수준("뻗기 전에 발을 올려라"). 베타("이 홀드를 잡아라")는 같은 문제의 완등 시도가 있어야 하고, 초반엔 본인의 완등 시도, 나중엔 서버로 모은 다른 사용자 클립으로
- 모델 학습은 안 한다. 인식은 기존 모델(Vision·ML Kit 관절, 홀드 검출은 공개 모델), 판단은 규칙 + 범용 비전-언어 모델. 사용자 클립은 완등·낙하가 영상으로 정해져 라벨이 공짜로 쌓이므로 학습은 나중에 가능해지는 선택지
- 촬영 조건: 삼각대 고정·정적 무브부터. 들고 찍은 영상은 카메라 이동 보정을 관절에 먼저 적용해야 하고, 다이나믹은 블러로 관절이 끊긴다. 둘 다 1층이 된 뒤 확장

## 설계 (4층)
1. **측정**: 시점별 손발 위치와 어느 홀드에 있는지, 골반 궤적·속도, 정지 시간, 낙하 직전 마지막으로 움직인 사지, 팔꿈치·무릎 각도. 힘 % 대신 "어느 팔에 매달려 있었나"를 자세(팔 펴짐 + 몸이 그 손 아래)로 근사
2. **루트 인식**: 프레임에서 홀드 검출 → 색으로 묶음. 국내 암장은 한 문제 = 한 색 홀드가 흔하므로 만진 홀드 색이 그 문제의 홀드 집합. 지금 위치에서 닿는 다음 홀드 후보를 기하로. 홀드 종류(저그·슬로퍼·핀치)는 뒤에서 찍으면 잡는 면이 안 보여 굵은 분류(볼륨·큰 홀드·작은 홀드)까지만. 대신 **당기는 방향**(언더·사이드풀·개스통)을 관절 배치로 추정하고, 체류 시간과 흔들림으로 "잡기 나쁜 홀드"를 간접 표시. 정면 사진은 선택 업그레이드
3. **근거**: 같은 문제의 완등 시도와 무브 순서표를 겹쳐 갈라진 지점. 문제 식별은 암장·홀드 색·벽면·기간
4. **코칭 문장**: 1~3의 결과를 구조화해 비전 모델에 키프레임과 함께 주고 문장 생성. 온디바이스 템플릿 문장이 대안

## 규칙 표 (2층 코치 항목)
| 코치가 보는 것 | 계산 |
|---|---|
| 손 뻗기 전에 발을 안 올렸다 | 마지막 손 무브 직전 N초 안 발 무브 유무, 발 높이 대 골반 |
| 팔로 당기며 버텼다 | 팔꿈치 굽은 채 머문 시간, 무브 간 정지 시간 증가 추세 |
| 무게중심이 지지 범위 밖 | 골반 x가 두 발 사이를 벗어난 정도, 낙하 직전 |
| 정적/동적 선택 | 마지막 무브의 골반 속도와 도달 거리 대 팔 길이 |
| 발이 미끄러짐 vs 손이 빠짐 | 낙하 직전 먼저 홀드를 떠난 사지 |
| 쉬는 자세 없음 | 팔 편 채 멈춘 구간 유무 |

규칙은 원칙이지 법칙이 아니다(발 떼기, 캠퍼싱, 다이노는 어기는 게 정답). 그래서 **판정이 아니라 관찰**로 말하고, 사용자가 "이건 아니에요"를 누르면 라벨이 되어 그 사람의 우선순위가 내려간다. 한 시도보다 **반복 패턴**("낙하 12번 중 9번이 발 안 올리고 뻗다가")에 무게

## 화면 (나중)
트림 화면에서 구간 하나 → "이 시도 분석". 결과는 타임라인 위 무브 순서와 낙하 지점(누르면 그 시점 재생) + 걸린 항목 문장. 관절 신뢰도 낮은 구간은 "잘 안 보였어요"로 표시하고 판단에서 뺌. 완등·낙하 초안은 구간 끝에서 사람이 위로 빠지면 완등, 아래로 떨어지면 낙하. 결과는 클립과 저장돼 암장 페이지에서 다시 봄

## 실험 절차
- 재료: 사용자가 주는 완등·낙하 영상(삼각대, 뒤에서). 같은 문제의 완등·낙하 쌍이 있으면 최선. 기존 IMG_5890(3분, 여러 시도)도 후보
- 도구: `scripts/joints.swift` (macOS). `swiftc -O scripts/joints.swift -o /tmp/joints && /tmp/joints 영상.mov out.csv [start] [end] [fps]`. 프레임마다 관절 15개(x,y,신뢰도)를 CSV로. 사람 여럿이면 직전 골반 위치에 가장 가까운 사람을 따라감. 신뢰도 0인 관절은 좌표가 쓰레기값이라 걸러야 함. 검출 규칙(`detect.swift`)은 건드리지 않음
- 분석: `scripts/analyze-joints.py` (numpy·matplotlib, 프로젝트 밖 venv). 무브 순서표(손목·발목이 멈춤→이동→멈춤 하는 시각), 골반 궤적, 낙하 시점과 마지막으로 움직인 사지, 팔꿈치 각도 시계열을 그림과 표로

### 1층 통과 기준
- [ ] 무브 순서표가 사용자가 영상을 보고 적은 순서와 일치 (사지·순서·시각 ±0.5초)
- [ ] 낙하 시점과 "먼저 홀드를 떠난 사지"가 사용자 판단과 일치
- [ ] 골반 궤적 그림만 보고 사용자가 낙하 지점을 짚을 수 있음
- [ ] 관절 검출률(신뢰도 0.3 이상인 손목·발목 비율)이 시도 구간에서 70% 이상. 아니면 홀드 매칭이 안 섬
- [ ] 당기는 방향 추정(언더·사이드풀)이 사용자가 보기에 맞음

### 코칭 문장 통과 기준
- [ ] 사용자가 어느 영상 것인지 모른 채 문장만 보고 자기 영상을 맞출 수 있음. 못 맞추면 일반론이라 실패

### 2026-10-01 루트 홀드 색 실험 (`scripts/holds-color.py`, 훈련 없음)
- 방법: `scripts/frame.swift`로 등반 전 기준 프레임을 뽑고, 관절 CSV에서 손발이 0.8초 이상 머문 자리(rest point)의 색을 기준 프레임에서 샘플 → 화면 전체 최빈 색상(벽 나무색, hue 0.097)을 배경으로 제외 → 채도 가중 색상 히스토그램 최빈값이 루트 색 → 같은 색상(±0.06)·채도 0.3 이상 픽셀을 덩어리로 묶어 상자
- 결과: **두 암장 모두 루트 색을 맞춤.** IMG_5110 빨강(hue 0.014), IMG_5634 초록(0.403). 5110은 빨간 홀드 8개 전부 상자, 오탐은 주황 홀드 1·분홍 홀드 1·테이프 1(색상 허용폭 0.06을 0.04로 줄이면 빠질 것). 5634는 초록 홀드 대부분 상자, 어두운 초록 TOP 홀드 1개 놓침
- 두 암장 다 한 문제 = 한 색 홀드였고, 테이프는 시작 홀드 표시나 번호표(TOP 6/7)로만 쓰임 → "만진 색 = 루트" 가정이 섬
- 함정: 배경 제외 전엔 벽 나무색을 루트로 잡아 벽 전체가 상자가 됐음. 기준 프레임에 사람이 서 있으면 그 자리 홀드가 가려짐(5110 rW 14s) → 다음은 구간 전체 프레임의 픽셀별 시간 중앙값으로 사람 없는 벽을 만들기(고정 카메라라 가능, 지나가는 사람도 지움)
- 결론: 2층 루트 표시는 색 기반으로 시작 가능. 홀드 검출 모델은 색이 겹치는 암장이나 흰·회색 홀드 문제에서만 필요

## 결론 (2026-10-01, 폐기)
- 1층(무브 순서·낙하 판정·낙하 직전 사지)은 세 영상에서 사람 판단과 일치했고, 색 기반 루트 홀드도 두 암장에서 루트 색을 맞춤. 기술적으로는 됐다
- 그런데 폰에서 결과를 본 사용자 판단은 "유용하게 쓰진 못할 것 같다". 이유: (1) 영상 위 스켈레톤·지지 다각형·유령 자세는 클라이머가 자기 영상에서 이미 보는 것의 재서술, (2) 부하 %·도달 %는 추정이라 행동을 바꿀 근거가 못 됨, (3) "다음엔 어떤 무브"는 발 낮음·골반 밖·멀리 뻗음 세 규칙으로는 실제 낙하의 일부만 설명, 나머지는 같은 루트의 완등 데이터가 있어야 함
- 다시 열 조건: 같은 루트의 완등·낙하 시도 쌍이 모여 "푼 시도는 여기서 달랐다"를 보여줄 수 있을 때. 그때는 단일 시도 추정치 없이 비교만으로
